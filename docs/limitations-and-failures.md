# Known Limitations and Failure Cases

> Why this document exists: **the error messages from `mikasa doctor` cite it directly** — when the
> health check reports a problem, the user should be able to read here what went wrong, why, and
> what to do about it. It is also an honest archive of every pitfall the project has hit: each real
> incident and lesson is linked from the code, instead of being scattered across chat history.
>
> Structure: ① ecosystem breakage ② known limits of the cleaning/parsing heuristics ③ known
> boundaries of design trade-offs ④ real bug cases from development (fixed, archived)
> ⑤ the evolution of what `doctor` checks.

## 1. Ecosystem Breakage: jieba and setuptools (2026)

**Incident**: new setuptools releases removed `pkg_resources`, which jieba 0.42.1 depends on
internally — `import jieba` is guaranteed to break on a fresh install (jieba#1043).

**Why pinning the version is not the answer**: the official stopgap is `setuptools<82`, but staking
the project's fate on a pin that can fail at any moment doesn't hold up (installing any other
package can bump setuptools).

**Mitigation (three layers of defence, see ADR-0008)**: use jieba when it is available; when the
import fails, fall back automatically to a pure-Python bigram tokenizer (zero dependencies,
deterministic); the version pins (`jieba==0.42.1` + `setuptools<82`) are only a performance
optimization. **When it reports a problem**: doctor checks `get_tokenizer_name()` — note that this
inspects the tokenizer **actually in effect**, not whether jieba can be imported (the first version
got exactly this wrong; see §5).

**From the user's point of view**: `mikasa doctor` reporting "jieba unavailable, tokenizer
downgraded to bigram" is not fatal but is a quality downgrade — see evaluation.md for the
difference in retrieval metrics; to restore jieba, run `pip install "setuptools<82"`.

## 2. Known Limits of the Cleaning and Parsing Heuristics

### PDF header/footer removal (loaders.py)

Heuristic rules: lines matching page-number patterns are removed; lines that repeat verbatim across
pages are removed wholesale (headers and footers are identical on every page, whereas body text
does not repeat verbatim). Known limitation: body lines that genuinely do repeat verbatim (code
blocks, quoted passages) become collateral damage — the probability is low and the blast radius is
predictable, so no machine-learning approach was introduced (the corpus is too small to justify
one). The sample PDFs are generated by `tools/build_sample_binaries.py`, which sidesteps the
problem.

### Two pitfalls when writing PDFs with PyMuPDF (tools/build_sample_binaries.py)

1. `insert_text` **silently wraps** a long line that exceeds the page width, and the wrapped
   continuation overlaps the line inserted after it and is lost — wrapping has to be done by the
   script itself against a character budget (a CJK character is roughly twice the width of a
   half-width one);
2. English lines are **silently truncated** once they reach x ≈ 595 pt (the page-width boundary,
   ≈54 characters at 10 pt), and the continuation is never rendered at all — the script uses a safe
   budget of 43 characters per line plus left-margin accounting (473 pt + 72 pt < 595 pt).

Two lessons: PyMuPDF's out-of-bounds behaviour is silent (no exception is raised), so any
write-side tool needs **post-write verification** (read back the line count and the content). The
script reads each sample PDF back for validation immediately after generating it.

## 3. Known Boundaries of Design Trade-offs

### MockLLM's heuristic decision (providers/llm.py)

MockLLM decides whether a question is supported by the material using the **longest common
contiguous substring ≥ 4 characters**, not a character-overlap ratio. The real lesson: with an
overlap-ratio rule, the common characters in a question (一/学/做/在…) push any corpus over the
threshold — "如何在一周内学会做菠萝包" ("how do I learn to make pineapple buns in a week") would be
misjudged as answerable. A contiguous run of ≥4 identical characters can only be a topic-specific
name or a content phrase (`正则化` / regularization, `防止过拟合` / preventing overfitting);
function characters cannot form a run of four.

It is still a heuristic (the mock only demonstrates the protocol; it produces no real semantics):
genuine refusal semantics come from the constraints in the system prompt, and the mock's
mis-answered samples (7/16 measured in evaluation.md §5) are precisely the evidence that **the
protocol layer is not the semantic layer**.

### Semantic continuity across turns (pipeline/ask.py)

v1 chat does not rewrite queries: a follow-up only injects the history into the prompt as a
compressed summary line, and retrieval still runs on the literal text of the current question.
Limitation: for pronoun or elliptical questions ("what are its drawbacks?") retrieval quality is
not guaranteed. The reason query rewriting is deliberately absent: a rewriter adds a second LLM
call (2× the cost and 2× the latency) and complicates the evaluation protocol — the summary
mechanism had to work first; query rewriting is an explicitly recorded v2 candidate.

### Three boundaries of the bilingual block (pipeline/ask.py, measured 2026-09-10, item #8)

1. **Translations "stop mid-sentence" — that is faithful to the source chunk being cut off, not a
   bug.** The chunker splits into fixed-length chunks by `chunking.size` (400 characters by
   default), so a chunk can itself end mid-sentence (measured on doc 71: one chunk ends with
   `…during repeated loading. As`), and the translation dutifully stops on the same half-clause.
   This is the same behaviour as the citation card, which has always shown only
   `snippet = content[:200] + "…"`. The first version truncated the original to 300 characters for
   display, which systematically cut a quarter off 400-character chunks and amplified the
   impression — it now uses a 500-character cap (see `_BILINGUAL_ORIGINAL_CAP`) and no longer
   truncates under normal configuration.
2. **Translations occasionally drop content**: on doc 71, `随着 successive 荷载循环` appeared (the
   Chinese for "with successive load cycles"), with "successive" left untranslated. The prompt
   allows English technical terms to be kept as-is, so this is model-quality variance; the parsing
   layer guarantees only the paragraph structure, not translation completeness.
3. **Produced only for "cited and English-dominant" chunks**: `is_english_dominant` requires ≥20
   ASCII letters and a CJK share below 20%, so fragments cut out of a chunk (e.g. a clause with
   fewer than 20 letters) are classified as non-English and skipped; Chinese chunks, refusal turns,
   and the mock backend never produce one at all.

### Single-process web deployment

`serve` is designed as a single process: an in-memory index snapshot plus a single-slot evaluation
task manager (architecture document §8). Known boundaries: it cannot scale horizontally across
workers, and an evaluation run occupies the evaluation slot. This is the deliberate shape of a
single-user demo machine, not a defect being papered over.

### The one-shot session-title boundary (M4.5)

A session is titled once, after the first turn, and does not drift with later turns — once a
conversation moves on, the title can be stale (the `fold_title` truncated form reflects only the
literal first question). The trade-off is recorded in ADR-0015 ①: titles should not shift every
turn, and manual renaming is the corrective path (rename from the menu, or re-run AI title
extraction at any time). Known gap: there is no mechanism that suggests a rename after the topic
drifts (a known-issues backlog item, not done because its value has not been demonstrated).

### Scale boundaries of the session tree (M4.5)

- `GET /api/sessions` keeps its limit=50: past 50 sessions the sidebar shows only the 50 most
  recent; older ones remain in the database but not in the tree (no search or pagination entry
  point; a known-issues backlog item);
- Folder expansion state is not persisted: refreshing the page collapses everything (ADR-0015 8);
- Deletion semantics: a folder can only be deleted when empty (409 with a count); there is no
  shortcut for deleting a whole subtree — a deliberate trade-off against accidental deletion
  (ADR-0015 4).

### SQLite version dependency surface (after the M4.5 migration)

The schema migration relies on `WITH RECURSIVE` (cycle-safe descendant queries) and
`ALTER TABLE ADD COLUMN ... REFERENCES` (no default means NULL, which is legal) — both
long-supported features of Python's bundled sqlite3. The project depends only on CPython's own
SQLite, never on the Windows system sqlite3.dll, so the version surface is the SQLite floor of the
Python version (3.13 ships ≥3.40); the migration tests cover pure in-memory and temporary
databases, so no cross-version differences need guarding. The rehearsal record for the first real
migration (v1→v2) is in the ADR-0004 revision section.

## 5. Evolution of What `doctor` Checks

The value of doctor is not in reporting a wall of OKs, but in **every check pointing at an
actionable next step**. How its scope evolved:

- Check semantics: dependency checks inspect **effective behaviour** rather than importability (the
  jieba case); key checks report only which environment variable name is missing and never touch
  its value; index consistency was promoted in M4 to a **three-way consistency** check (the
  meta.json snapshot × the vector row count/dimension in the database × the current configuration —
  the DB is authoritative, the snapshot is derived; any mismatch tells the user to run
  `mikasa ingest --reindex`, see ADR-0014 ④);
- Upper bound enforced: Python ≥3.14 fails immediately as unverified (the lower bound is guaranteed
  by `pyproject.toml`);
- Local-inference gating (M4): Ollama connectivity and whether the model has been pulled are
  checked only when `llm.backend == "local"` (with `ollama pull` guidance and a Windows
  `OLLAMA_BASE_URL` escape hatch in the message), and fastembed importability only when
  `embedding.backend == "local"` — offline/api notice nothing; the probe functions are module-level
  implementations (unit tests replace them wholesale, so doctor never really connects to an
  external service); doctor **does not trigger an embedding-model download** (constructing
  TextEmbedding pulls ~100 MB, so downloading belongs to the runtime of the first ingest or
  question);
- Levels and failure exit: doctor is a **hard gate** — any failing item produces a summarized red
  line, categorized troubleshooting advice, and exit code 1 (an early version of this document said
  optional-dependency failures only warn; that did not match the code and has been corrected: a
  missing optional dependency is a failure too, and it is the message's job to say what to install
  and where to get it); the key requirement splits three ways — none needed for mock /
  none needed for local (Ollama's /v1 does not check Authorization; the provider layer injects a
  placeholder key, see ADR-0014 ①) / strict for api — and a single table covers all three.

**Declared blind spot**: doctor checks only the *environment and static consistency*, never
*retrieval quality* — that is what the evaluation (`mikasa eval run --profile offline`) answers.
The two run back to back in CI; do not use doctor as a quality gate.

## 6. Real Bug Cases from Development (Continued, 2026-09-11)

### Systematic page-number drift: the same bug in two places (ingest/loaders.py)

`load_pdf` numbers pages with `enumerate(cleaned, start=1)`, and "one page, one element" is a hard
invariant. But `_drop_page_furniture` and `_cut_reference_tail` each contained an `if kept:` /
`[t for t in rest if t.strip()]` that filtered pages left empty by the cleaning out of the list —
with enough blank pages (pages 3, 5, and 7 of doc 71), every later page number shifted
systematically forward, measured at +3 to +5. Together, the two sites cut a 301-page document down
to 189 pages, with the earlier pages misaligned as well. **Lesson: an invariant like "list position
is identity" has to be verified at every consumption point** — the first fix touched only
`_drop_page_furniture` and the drift persisted; the second site was found only by working backwards
from "189 pages after the cut".

### Ollama's runtime context window is only 2048 (the model itself supports 40960)

qwen3:8b declares 40960, but the Ollama runtime defaults to `num_ctx=2048` — a 6000+ token prompt
was silently truncated at 2050, and truncated **from the start**: the system prompt (citation
protocol, refusal rules) may never have reached the model at all. The canary test: a long block of
filler text with a question-opening canary buried in the middle returned nothing before the fix and
answered everything correctly after setting `OLLAMA_CONTEXT_LENGTH=16384`. This is also the larger
half of the root cause behind "retrieval doesn't give the model enough" — injecting 10 chunks
(~3500 characters) was already over the window. Mikasa.bat now hardcodes that environment
variable.

### The windowed build never wrote a log file: the fix landed on the CLI entry point, which double-click never goes through (packaging/entry.py)

The packaged build is compiled with `console=False` (no black window on double-click), so a failed
startup only shows one message box: "detailed log at `%LOCALAPPDATA%\Mikasa\logs\`" — which makes
that file the user's **only** diagnostic. On review it had never been written to: the whole repo
passed `log_file=` to `setup_logging` in exactly one place, `cli.main()`, while the double-click path
is `entry.py: main() → _serve_forever()`, which imports only `mikasa.web.app` and **never goes
through cli.main()**. The no-argument `setup_logging()` triggered by the first `get_logger()` inside
the package attaches a console handler only, and in a console-less build that is the same as
dropping records into the void. Measured evidence: `_CONFIGURED=True` with a handler list of just
`['RichHandler']`. The fix consolidates "where logs live" into one definition,
`utils.logging.default_log_file()`, shared by both entry points, and the message box now shows a
**real, copyable** path (it used to be a literal `%LOCALAPPDATA%` the user could neither click nor
locate). The regression test `tests/unit/packaging/test_entry.py` loads entry.py by path and asserts
a FileHandler is genuinely attached and genuinely receives writes. **Lesson: fixing one entry point
is not fixing them all — the packaged form has its own entry point (double-click ≠ the `mikasa`
command), so the patch belongs on what both paths share.** Bug of this kind is invisible until
packaged: 431 tests could pass in source form and it would still ship broken.

### Text cannot be selected or copied in the desktop window (packaging/entry.py, reported by the user 2026-09-11)

The report: "text can no longer be selected and copied in the page." The root cause is not our code:
pywebview's `create_window(text_select=...)` **defaults to False**, and in that state it injects
`body { user-select: none; cursor: default }` into the page (see `webview/js/customize.js`:
`var disableText = '%(text_select)s' === 'False'`), leaving **every character in the window
unselectable**. For a document-QA app that is crippling — answers, quoted source text, and evaluation
reports all need to be copyable. The fix is `create_window(..., text_select=True)`, with a regression
test that injects a fake webview module and asserts the kwarg. **Lesson: a shell library's defaults
are chosen for a generic window, not for this application — when wrapping one, walk through every
default that changes user-visible behaviour.** The same JS block revealed `zoomable=False` (the
default), which `preventDefault`s Ctrl+wheel even though this app never binds that gesture
(recorded, not changed), while `easy_drag=True` **only applies to frameless windows**
(`platform == 'edgechromium' and easy_drag and frameless`), so a framed window is unaffected.

### Text cannot be selected in continuous scroll: a deliberate trade-off the user overturned, and a virtualization trap (reader.js)

The page view is a bitmap, so selection depends on a transparent text layer. That layer used to be
built **only in single-page mode**, with an explicit comment: "continuous mode with hundreds of pages
means tens of thousands of spans and the DOM cannot take it (switch to single page if you want to
copy text)." After the user tested it on 2026-09-11 and asked for selection in continuous scroll too,
the only way forward was virtualization.

**The trap: the first version used an IntersectionObserver ("materialize whatever enters the
viewport"), and acceptance measured 15 of 24 pages materialized.** Root cause: page images are
`loading="lazy"`, so before an image loads its node is ~0 high and hundreds of pages fall inside the
viewport test at once (including the ±1200px margin) — meaning every page's text layer is requested
simultaneously, which is exactly the thing we set out to avoid; a 301-page paper would degrade into
"301 requests and hundreds of thousands of spans at startup". Switching to a **page-number** window
(current page ±2, synced at page boundaries) pins it at 5 layers with no dependence on image
loading. **Lesson: when the geometric quantity you are judging by is itself produced by
lazily-loaded content, stop judging by geometry — find an equivalent that does not depend on load
state** (here, page-index distance).

Two method notes that came with it: (1) an acceptance script must use a **real mouse drag** (CDP
`Input.dispatchMouseEvent`) and then read `getSelection()` — constructing a range through the
Selection API bypasses `user-select: none` and yields a **false pass**, precisely for the failure the
user was hitting, which lives in CSS; (2) an empty library pops the first-run onboarding panel, which
**covers the whole page**, so acceptance must wait for it to appear and dismiss it (it races: it is
attached only after `/api/health` returns, later than "page ready"; a plain `if` misses it and every
subsequent drag lands on the panel — the measurement in fact selected the panel's own text).
