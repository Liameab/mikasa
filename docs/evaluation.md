# 自动化评测（M2）：设计口径与使用指南

> 配套代码：`src/mikasa/eval/`（评测编排 + `synth.py` 自动出题）、
> `tools/build_golden.py`、`evals/questions.yaml`、`evals/golden_set.json`。
> 命令：`mikasa eval run | list | compare`；**自动出题的入口在 Web 评测页**，不在 CLI。

评测要回答的不是"模型好不好"，而是三句可以拆开回答的话：
**要的资料有没有被捞回来（检索）**、**回答有没有按规则引用并守住拒答（生成协议）**、
**回答内容对不对、完不完整（语义）**。三句话成本与依赖逐级上升，
因此评测拆成三个阶段跑，每阶段用不同的配置口径，结论互不掩盖。

## 1. 三阶段口径

| 阶段 | 测什么 | 配置口径 | 指标 | 离线可跑 |
| --- | --- | --- | --- | --- |
| A 检索层 | 融合召回有没有把题面素材带回来 | 关重排（融合窗口独立锚定 10，与 api/offline 档当前值相同；local 档是 14） | recall@5/8/10、MRR、nDCG@k（按难度分层） | ✅ |
| B 生成层 | 引用纪律 + 拒答纪律 | 产品配置原样（重排开 `top_n=8`、窗口 10） | citation gold ratio、引用越界率、可答误拒、拒答准确率 | ✅（mock LLM） |
| C 语义裁判 | 回答内容质量 | LLM-as-Judge（双轮位置交换） | 正确性 1-5、档位 A-D、忠实性、两轮一致性 | ❌ 需密钥/本地裁判 |

为什么阶段 A 要"关重排"：重排器可能把题面素材挤出前几名——那是重排的失误，
不是召回的失误。检索层评测要把召回与重排解耦，只回答"素材在不在候选里"；
阶段 B 才回到产品配置（重排开 `top_n=8`），测真实链路端到端表现。融合窗口 A 定 10、
B 走产品配置（api/offline 档 10、local 档 14——63 题真实验收实证：窗口 8
会漏 hard 综合题的第二金块，q036/q037
实测金块落在第 9-10 名，@10 时 47 题 recall@10=1.000）——A 的窗口由
runner 常量独立锚定，产品将来调小也不动摇 A 口径。两个口径都在同一份报告里披露。

## 2. 黄金集：两套题库 + 题对不上库的防错配

**内置题库是人写的**（`evals/questions.yaml`，63 条：47 可答按 easy/medium/hard
分级 + 16 不可答按 unrelated / insufficient / hallucination_bait 分类），不是自动生成的——
人工题的价值在于它不会顺着语料的措辞出题，自动生成只会把语料的偏见再学一遍。

**自动题库**（2026-09-19 起，`src/mikasa/eval/synth.py`；**入口是 Web 评测页**——
`POST /api/eval/synthesize`，产物落 `<数据目录>/eval/golden-auto.json`，CLI 没有对应子命令）补上另一半：人工题的锚句
是示例语料的原文，**换一份语料就天然失效**，而"评我自己的资料"这件事没人替你的文档
写过标准答案。自动出题从你自己的语料里抽样分块，让模型出一道"只有这段能回答"的题，
**那个分块即标准答案**，于是任意语料都能评。代价必须写在报告里：自动题是模型照着
自己看过的原文出的，比人工题简单、分数天然偏高，**只能横向比**（同一份题库下比较两次
检索改动），不能跟人工题的绝对分比——报告首部以「**自动生成**」显式标注。

防错配（2026-09-19 起）：

- **锚句唯一命中**（仅内置题库）：每道可答题携带从语料原文逐字摘录的锚句（anchors）。
  `tools/build_golden.py` 把锚句解析成真实 chunk_id 时，零命中（题面与语料对不上）
  或多命中（分块重叠有歧义）都**拒绝冻结**，一次报全所有问题；
- **分块级冻结**（两套题库都有）：每道可答题连同它标准答案分块的 content_sha256
  一起落盘。评测前**逐题**核对"这一块还在不在、内容变没变"：变了的题**跳过**，
  报告首部写明跳了几道、正文逐条列出题号与原因；全题被跳过才是硬错误。

  **口径变更**：原先比的是**全库**指纹（哈希 (chunk_id, content_sha256) 序列）——
  往库里加任意一篇文档、改个标题都让整份题库作废报错，而真正的风险只涉及题目引用的
  那几十个分块，守卫范围远大于风险范围。改成分块级之后，不相干的增删不影响评测，
  该拦的照样拦得住：`--reindex` 让 chunk id 整体平移（旧 id 查不到 → 跳过）、某个
  分块内容被改写（哈希不符 → 跳过）。之所以要"跳过而不是放行"：静默用错位的标准
  答案算分，会跑出看着正常、其实毫无意义的数字——这是评测工具最怕的事。之所以
  要显式留痕：静默缩小分母会让分数看着变好。

注意一个坑：分块器在相邻块之间会保留**重叠窗口**（块尾句子重复出现在下一块），
这类句子不能选作锚句；PDF 长行在 loader 阶段被折行插入换行符，锚句必须落在单行内。

```bash
mikasa ingest sample-corpus      # 1. 语料入库
python tools/build_golden.py     # 2. 冻结黄金集（幂等；语料变了就重跑）
mikasa eval run --profile offline   # 3. 跑评测（零密钥）；只有 api 档开语义裁判
                                    #    （local 档 judge.enabled=false，见 ADR-0014 ③）
mikasa eval list                 #    历史评测回溯
```

## 3. 指标口径（全部手写，不引评测库）

- recall@k = |G ∩ R[:k]| / |G|——题面金块集合 G，检索返回 R。
  多金块时每块各算一次命中比例；
- MRR = 首个金块排名的倒数（未命中 0）；nDCG@k 对多金块排序质量整体打分；
- **citation gold ratio**：回答引用块中命中 G 的比例（只在"有引用"的样本上统计）。
  这是语义裁判缺席时召回侧的代理指标，不与真正的引用精确率混称；
- **拒答准确率** = 干净拒答数 / 不可答题数。干净拒答 = 总数 − 误答 − 拒答却带
  引用标记（L3 违规，理论上不可达，出现即协议 bug）；
- 越界/自造编号率：正文全部 `[n]` 标记中，编号超出注入片段 1..N 的占比——
  模型自造编号是引用格式纪律的核心信号，对标真实 RAG 产品里的"引用解析失败"。

逐条值用 `_Mean` 容器累加，报告期 `summarize` 输出 mean / p50 / p95 / min / max / n，
难度分层与总体共用同一批逐条原料，口径透明。

### 3b. 不确定度：置信区间与配对比较（2026-09-25）

63 题上的**单点数字没有不确定度**——改一次检索拿到 recall@10 从 0.98 到 0.99，
光看这两个数没人答得上"这是变好了还是噪声"。补两个口径：

- **均值的 95% 置信区间**（阶段 A 表新增一列）：对**题库**做 bootstrap
  重采样（2000 次，种子写死）。读作"若从同一分布的题库里另抽一批题，
  均值大概会落在哪"。**种子固定的理由**：同一份数据两次渲染必须得到同一个
  区间，否则"上次 0.82、这次 0.79"分不清是模型变了还是重采样变了。
  它不覆盖语料变动与模型版本漂移——那些归指纹核对与逐题校验管，不在统计里。
- **`mikasa eval compare <旧> <新>`：逐题配对比较**。这是更强也更有用的那个
  检验：**两次独立跑的均值差会被题间方差淹没**（63 题里几道难题的正常波动，
  比一次检索改动的真实效果还大），而配对只看"同一道题变了多少"——没变的题
  自动抵消。输出差值均值 + 95% 区间 + `显著`（区间**不跨 0**）。

**两条边界要如实说**：① 区间只对**这一批题**成立，题库本身就是样本，它不是
物理定律；② 配对要求两次运行都有逐题留痕（2026-09-25 之后的运行才有），
共同题少于 5 道时命令直接拒绝出结论而不是硬算。分层样本（如 hard 只有
12 题）的区间会宽得多，读到"hard 掉了 2 个点"时先看区间。

## 4. 语义裁判（阶段 C）的三个偏差修正

LLM 当裁判有自偏好、位置敏感、量尺漂移三类已知偏差，逐一处理：

1. **位置交换**：同一判题把【参考答案要点】与【候选回答】位置颠倒问两轮。
   两轮一致才采信进分数统计；不一致（含格式解析失败）单独披露为 inconsistent——
   不一致本身是"生成不稳定/裁判敏感"的信号，报告列在异常明细里供人工复核，不抹平；
2. **双量尺**：每轮同时要求 1-5 分数制与 A-D 档位制。档位与分数独立判断，
   报告披露一致样本的 A/B 档占比；
3. **跨厂商**：裁判与生成端默认不同服务商（生成 DeepSeek / 裁判 SiliconFlow
   Qwen，`api` 档即此约束；`local` 档都走 Ollama）。配置层落实，报告披露当次配置。

解析依赖固定格式行（`正确性评分: N/5` / `档位: X` / `忠实性: 是/否`），不依赖
JSON mode——Ollama 小模型不稳；解析失败计 raw 留痕。裁判对可答题且未拒答的样本
判分；拒答与空答案短路不判（正确性由拒答桶负责），判题素材 = 题面金块原文拼接
（上限 3000 字符，控成本且让各题成本公平）。

**NoJudge（仅协议层）**：judge 未启用或 api 密钥缺失时自动降级为 NoJudge，
报告显式注明"仅协议层指标"。offline/CI 场次没有语义分，这是设计好的
缺省形态——三端行为同构，只差配置。

## 5. 已知边界与限制（诚实清单）

- **offline 的 mock LLM 无语义**：它只演示引用协议（问题与语料有 ≥4 字连续
  重叠就引用作答，否则拒答），所以 offline 场次的 citation gold ratio、拒答
  准确率是"协议层自检"，不是真实质量。实测 63 题里 7 道不可答题被 mock 误答
  （bait 5 中 4、insufficient 5 中 3，其余干净拒答）——误答恰是 mock 局限的
  实证，也说明真实语义必须靠阶段 C；
- mock 自带的噪声说明：offline 场次拒答准确率 ≠ 产品拒答能力，勿拿它对外汇报；
- **真实 api 档对照（2026-09-09 验收基线，DeepSeek 生成 + Qwen 裁判）**：
  ⚠ **配置脚注**：这两条 09-09 基线跑在旧链路参数上（api 档 `reranker.top_n=5`、
  local 档 `fusion_top_k=10`、本地档当时还没有 `think`/`num_ctx` 两个旋钮），
  与当前默认值不同，**绝对数不可与新跑的结果直接比**（ADR-0017 ④ 原话：
  改 `top_n` 会平移基线）。它们仍是"真实质量量级"的证据，不是回归对照。
  阶段 A recall@10=1.000 / MRR=0.979 / nDCG≈0.98（hard 12 题 recall@5=0.972）；
  引用越界率 0.000、citation gold ratio 均值 0.848（p50=1.000，44 题样本）；
  16 道不可答拒答 16/16（真实模型守住纪律，mock 的 7 误答在此归零）；
  可答误拒 3/47——其中 q036 检索漏了第二金块（真缺料，拒得合理），
  q021/q031 资料完整支撑下模型仍保守拒（提示词规则 4"部分覆盖就答"的
  边界，继续放权会威胁不可答纪律，按已知边界接受）；
  裁判双轮一致 36/44（不一致 8 条多为 4/B vs 5/A 边界与个别忠实性翻案，
  裁判噪声 >10% 时先怀疑裁判模型再怀疑生成）；正确性均值 4.83、A/B 档 100%。
- **真实 local 档对照（2026-09-09 run #5，qwen3:8b 生成，judge 关闭 → 仅
  协议层指标）**：阶段 A recall@5=0.975 / recall@10=0.982 / MRR=0.940——
  easy/medium 全 1.000，差距全在 hard 12 题（recall@10=0.931），即 512 维
  bge-small 相对 api 档 1024 维 bge-m3 的损失集中在最难档；阶段 B 引用越界率
  0.000、L3 违规 0、可答误拒 0/47（api 档保守拒的 q036 等本地档全部作答——
  语义质量无裁判确认，仅协议合规）；citation gold ratio 0.798（n=47）；
  **拒答 13/16**：q057/q058/q059 三道不可答误答全是"模型预训练记得的外部
  知识"型（含故意埋的 hallucination_bait q059——哨兵如期咬住小模型），
  即本地小模型倾向作答而非拒答，与 DeepSeek 的保守拒答互为镜像；
  零成本换 3/16 拒答纪律失守，取舍记录于 ADR-0014 ③/⑤；
- **M4.1 勘验（2026-09-09，同指纹同配置全量复现 + 消融，结论=均接受为
  local 档边界）**：①hard 漏检精确到 q036 第二金块 155（梯度下降块）与
  q041 第三金块 126（缩放点积注意力块）——融合名次 14/16/24，fusion_top_k
  10→20、bm25/dense 子窗口 20→40 消融对 recall@10 **零变化**（窗口放宽
  不改前 10 排序；子窗口扩大只把 155 从 24 提到 16）——缺口本质是
  多金块难题的"答案跨块"：金标按答案逻辑标 2-3 块，双路检索按相关度
  单峰排序（api 档 bge-m3 时代第二金块亦贴边 9-10 名，见 runner.py 注），
  调参路线实证无效；②拒答 3 误答形态勘验：q057 编引用作答（借 KNN 块
  撑话）、q058 裸答零引用（知无料仍答）、q059 幻觉答 + 引用张冠李戴
  （论文块撑作者数）——提示词规则 3"哪怕你知道答案"与示范（"地球半径"
  同类例）已全覆盖、DeepSeek 同规则 16/16，证规则有效而 qwen3:8b
  服从性不足，强化提示词边际收益低且动共享协议需全档回归；③citation
  gold ratio 0.798 同属生成模型引用精度（p50=1.000，少数题部分不中）。
  可选项记录：换 qwen3:14b（8G 显存吃紧、生成显著变慢，不保证归零）；
  开 local 重排器需 fastembed 版本选型（ADR-0014 ②）——均非低成本收益；
- 裁判开销：每题两轮 × 63 题，api 档全量跑约 126 次判题调用，按题量线性；
- 重排器与稠密向量在阶段 B 的线上效果依赖本地模型/密钥，CI 只覆盖协议层。

## 6. 读报告指南

`data/eval-reports/{run_id:04d}-{name}.md` 与 `eval_runs` 表同源（report_md 列）。
固定章节：

- **阶段A 表**：先看 recall@10 有没有 ≥0.95——没有则先查分块与检索，别急着调模型；
  同表的 **95% CI（均值）** 是那个数字的不确定度（见 §3b）：区间宽到跨过你的
  判断线时，先把题库做大或看配对比较，别对着小数点后第二位下结论；
- **阶段B 表**：可答误拒 >0 查"拒答阈值是否过紧"；未拒答却零引用 >0 查引用
  提示词；拒答准确率 <1 去异常明细看逐题（误答集中在哪种 reason 分类，据此
  补提示词或补语料）；
- **阶段C 表**：双轮不一致率是健康信号，>10% 先怀疑裁判温度/模型，再怀疑生成不稳；
- **异常明细**：链路失败、误拒、误答、L3 违规、裁判不一致逐条列出——这是
  人工复核的入口，正常条目请查 metrics_json 的 items 逐条留痕。

回归门禁口径（CI）：全量 `pytest -q` + `ruff` + `mypy` +
`mikasa eval run --profile offline` 冒烟。**覆盖率基线：92%**（9004 语句 / 731 未覆盖，
2026-10-07 全量重测：**1188 passed + 2 skipped、1 分 46 秒**；
`--cov=mikasa --cov-report=term`。上一版 92% = 8912 语句 / 1170 passed（2026-10-05 全量审查）；
再上一版 92% = 8594 语句 / 1136 passed（2026-09-30）；
再上一版 92% = 8578 语句 / 1126 passed（2026-09-27 MCP 轮）；
再上一版 92% = 8190 语句 / 1085 passed（2026-09-25）；
再上一版 93% = 3469 语句 / 2026-09-09 M4.5 收工——语句数翻了近一倍而比例只降
一个点，是"新增功能都带测试"的结果）。
真实质量验收（发布前人工跑）：`--profile api`（DeepSeek 生成 + Qwen 裁判，
阶段 C 判分）；`local` 档 judge 关闭（ADR-0014 ③）→ 只看协议层
（召回/引用纪律/拒答），语义质量对照以 api 档近似。

## 7. 结构化输出 A/B：JSON 承载 vs 文本标记（2026-09-27）

**为什么做**：`pipeline/prompts.py` 开头那句"用纯文本标记而非 JSON 结构化输出"
决定了 `[n]` 协议的**承载方式**，却从未被测量——它是一条写在注释里的假设
（ADR-0037 把它变成了默认关的开关 + 一次对照实验）。

**协议与路径**：编号仍是**注入顺序**，模型无权自造编号；两条路径的提示词
差异可枚举（只多 JSON 契约 + 来源行的 `chunk_id`），因此差异**只有序列化层**。
场次：`mikasa eval run --profile api [--config 开关覆盖层] --name api-marker|api-json`
（同一份 63 题、同一份语料 sample-corpus、同一档嵌入 bge-m3）。

> **提示词版本提示（2026-09-30 补注）**：本节（含 §8）的生成侧数字产生于

> **这两个"配对"列的口径**：两列均值取自两场**各自的报告**，分母是"可答题里未拒答且
> 有引用的样本"（n=46）；配对列按**两场共同题**算（n=45，2000 次 bootstrap、固定种子，
> 与本仓 `eval compare` 同一函数）。两者分母不同，"均值差"与"配对差"因此不完全等值
> ——单场均值去掉的是各自丢的那一题（见下）。

**9 次格式失败的构成**（逐条来自运行日志）：8 次 `chunk_id` 错配 + 1 次"正文与声明不符"。
错配的样子很说明问题——`marker=5 声明 55、实际 54`、`marker=6 声明 38、实际 39`、
`marker=7 声明 3118、实际 56`：模型把 `chunk_id` 写成了**邻块编号或多位乱数**。
**受约束解码约束的是形状，不是内容**：schema 保证它吐出一个整数，不保证那个整数是对的。
这条是本轮最有价值的一句——`format: <schema>` 的宣传很容易被读成"格式问题解决了"，
实测是"语法问题解决了，语义问题原样保留，且因为有了结构化的壳，失败反而更难被发现"。

**结论（local 档）**：在 8B 上，JSON 承载**只留下代价**——输出 token −44.5%、
答案长度 −60%、分节与列表几乎归零（模型把预算花在填字段上，回答被挤成短句），
换来的是拒答纪律与引用命中率**都没变**（差异全在重跑噪声内）。
把这条和 §7.1 并排看：**同一个改动在两个模型上的收益符号相反**——
DeepSeek 上 JSON 承载改善了拒答（误答 3→1），代价 +12% token；8B 上它只留下代价。
`pipeline/prompts.py` 开头那句"用纯文本标记而非 JSON，对小模型更稳"由此从"觉得"
变成了**实测**：它是对的，而且现在知道了代价有多大。

**重跑噪声（读上面任何差值前先看这一段）**：同一配置隔夜跑两次（#1 → #2），报告口径的
单场均值是 citation gold **0.850 → 0.817**（差 −0.033）；按共同 45 题配对则是
**0.846 → 0.835**（Δ−0.011，CI [−0.041, +0.007]）。两者不等，是因为两场**各丢 1 题**
（超时，且不是同一题：q038 / q033）——分母不是同一批题。所以本档位 **±0.04 以内的均值差
不该被当成效果**——marker 与 json 的 −0.007 就落在里面。报告里那些**计数**（格式失败 9/62、
拒答 11/16）比均值稳，这也是它们更值得引用的原因。

**顺带发现（2026-09-29 已修，见 known-issues E5）**：local 档 `llm.timeout_seconds`
默认 60s，而本档 `max_tokens=4096` 的长回答偶尔跑过 60 秒（两场各 1 题超时丢题）。
本次两组同配置、各丢 1 题，配对按共同题算，不影响上面的结论。
**修法**：`config/profiles/local.yaml` 单列 `timeout_seconds: 180`——按本档实测
~16.4 t/s 折算约 3000 token 的余量，落在 4096 上限内；且两场日志无显存驱逐记录，
"显存抖动卡住"这条解释已排除（补证见 `known-issues.md` E5）。
**这条改动平移本档基线**：此后 local 场次不再丢题，与上面 #1/#2/#3 的数字比较时
留意分母差异（那三场是 60s 配置下的历史场次）。

### 7.3 这次实验的另一份产出：一个真 bug

第一轮 api-json 跑完发现日志里 **63 条"查询翻译失败"**（api-marker 是 0 条）：
结构化开关当时挂在 provider 配置上，于是**所有非流式调用**（查询翻译、双语对照、
会话标题提炼）都被切成了 JSON 模式，跨语言第二路整场静默失效。
修法是"配置只决定答案生成要不要结构化，provider 只认显式传参"
（`complete(..., structured=True)`），并补了回归测试；**四场次因此全部重跑**，
上表用的是同一份代码下的结果。
这条正是"评测要能发现副作用"的实例：功能开关的**作用域**比它的默认值更容易出错。

## 8. LangChain 对照组：框架默认链 vs 本仓协议层（2026-09-29）

**要回答的问题**：检索能换框架，那**生成/引用这一层**呢？框架的默认 RAG 链替我们做了什么、
又漏了什么。这一节是实测。对照目录 `experiments/langchain_baseline/`（**对照，不底座**：
不进 `src/`、不进主 CI、依赖树 63 包 / 253 MB）；完整逐题数据与复跑命令见该目录 README。

**口径（先说清楚，否则数字没有意义）**：两边吃**逐字相同**的 14 块上下文（快照里生产注入
窗口的顺序），框架侧**不自己检索**、自研侧也不检索——差的只有生成这一层。模型同（qwen3:8b）、
温度同。框架侧用任何一篇"LangChain RAG 入门"里拿到的东西：
`RetrievalQA.from_chain_type(chain_type="stuff")`——默认提示词（资料拼成一段、**没有编号**）
+ `StrOutputParser`（**没有校验**）。自研侧走产品代码 `Generator`。

| 指标（63 题：可答 47 / 不可答 16） | LangChain 默认链 | 本仓协议层 |
| --- | --- | --- |
| 回答里出现 `[n]` 标记的比例（可答） | **0.0%** | 100% |
| 每份回答平均标记数 | 0.00 | 3.49 |
| 越界标记率 | 0.0%（空集） | 0.0% |
| 拒答率（不可答 16 题） | **0 / 16** | **10 / 16 = 62.5%** |
| 平均字数（可答） | 340 | 302 |
| 分节 / 列表项（每份均值） | 0.00 / 0.70 | 1.15 / 1.91 |
| 单题中位耗时 | 14.8s | 11.7s |
| 输入 / 输出 tokens | 151,882 / 11,955 | 212,181 / 9,940 |

**怎么读这张表**：

1. **框架那列的"越界率 0%"是空集上的 0**。63 题里框架**一次都没有输出过 `[n]`**（逐题核对，
   `any(markers)` 为假）——没有编号系统，就没有"越界"可言。这一格不能读成"框架的引用也规范"。
2. **拒答 0/16 是这一节最硬的一条**。16 道库里没有答案的题，框架**全部**给出了实质回答
   （严格、宽松两个口径都是 0）——默认链从不拒答。这既是幻觉的来源，也是"协议层为什么必须
   自己写"的直接证据：它不是格式偏好，是**防幻觉的一道门**。
3. **代价是输入 token +39.7%**（212,181 vs 151,882）：编号、引用规则、拒答规则、示例都写在
   提示词里，这是要付的钱。中位耗时反而快 21%（拒答短），输出 token −16.9%。
4. **呈现形态也是协议层的产物**：分节 1.15 vs 0.00、列表 1.91 vs 0.70——产品提示词规定了答案
   怎么组织，框架默认提示词不管这个。

**检索层的同款对照（结论，表在对照组 README §3）**：47 道可答题、同一份语料与 embeddings，
recall@5/8/10 两边**完全相同 0.982**（配对差 0），MRR 0.924 vs 0.911（Δ−0.012，CI
[−0.035, +0.000]，不显著）。逐路诊断把差异定位到了一处：**稠密路 top-20 两边 47/47 逐题一致，
BM25 路 0/47**——差异全部来自 BM25 的 IDF 公式（框架用 `ln((N−df+0.5)/(df+0.5))` 加负值兜底，
本仓用 `ln(1 + …)` 恒正），不是"框架的向量检索更差"。检索耗时两边都在**毫秒级**
（1.2ms vs 0.4ms），而同一批问题的查询嵌入要 40.8ms——**别为性能换实现**的实测依据。

**不能推广的地方**：① 框架那列用的就是**默认链**，换个提示词就能补上引用与拒答——但那恰恰是
要说的事：**框架给的是管道，协议要自己写**，写在框架里也一样要写。② 这是 local 档；
api 档（DeepSeek + bge-m3）同款对照未跑，成本与速率都由对方决定。③ 拒答 10/16 与 §7 评测档的
11/16 略有差别，因为这份对照用的是**冻结的生产注入窗口**（不含跨语言第二路），不是评测那条
检索链路——两边量的是同一件事的不同入口。

## 9. MCP 工具调用评测：把库挂给 agent 之后（2026-09-30）

**为什么要测**：MCP（ADR-0036）把知识库变成三个只读工具，但"给了工具"不等于
"会被正确使用"——工具选择、调用次数、引用是否仍可验证，都得实测（谈判稿 §4-B）。
这一节测**模型那一侧**；"协议层对不对"由 `tests/unit/mcp/` 与 Claude Code 的真实
轨迹各自覆盖。

**怎么测**：`tools/eval_mcp_tools.py`——脚本自己就是 MCP 客户端（真起
`mikasa mcp` 子进程、走 stdio JSON-RPC），再套一个最小 agent 循环：工具清单从
`tools/list` 现取、转成 Ollama 原生 `tools` 交给 **qwen3:8b**，**由模型自己决定
调谁**（不是脚本写死的策略，否则测不出"工具选择"）。10 题按规则从 golden_set 现选
（6 可答：easy/medium/hard 各 2；4 不可答：unrelated×2 / insufficient /
hallucination_bait），语料 = sample-corpus 隔离库，`temperature=0`、`think=false`。
三个场次跑**同一批 10 题**：

1. **基线臂**：默认驾驶员提示词（"涉及知识库内容时必须调用工具，不要凭记忆回答"）；
2. **加固臂**：`--strict-tools`，比基线只多一句"**即使你认为自己知道答案**，也必须
   先调工具"；
3. **ask 探针**：`--probe-ask`，不让模型参与，逐题直接调 `ask` 核对引用。

| 指标（10 题） | 基线臂 | 加固臂 | ask 探针 |
| --- | --- | --- | --- |
| 工具调用总数（agent 侧） | 8（search 7 / read 1） | 11（search 10 / read 1） | 10（全是 ask） |
| **用了 `ask` 的题** | **0 / 10** | **0 / 10** | 10 / 10 |
| 凭记忆作答（一次工具都没调） | **2**（q048 天气、q049 拿铁） | 0 | — |
| 可答题"只搜不答"（答了但没有引用） | 6 / 6 | 6 / 6 | 0（ask 全答出来了） |
| **假"知识库中没有"**（可答题被答成没有） | 1（q017） | 1（q017） | **0** |
| 引用可验证性 | 无引用可验 | 无引用可验 | **12/12 chunk_id 可 read 回、0 越界** |
| 不可答题的处置 | 2 凭记忆作答 + 2 如实说没有 | 4/4 如实说没有 | 4/4 `refused=true` |
| 单题中位耗时 / 总耗时 | 10.4s / 153s | 13.9s / 161s | 9.4s / 106s |

**三条结论**：

1. **8B 只会用 `search`**：20 次 agent 侧调用里 19 次 search、1 次 read、
   **0 次 ask**。对照 2026-09-27 Claude Code 的真实轨迹（**换 6 个查询词**再搜 →
   read → ask、无依据时如实拒答）——"工具可用"与"工具会用"之间的差距整段落在模型
   这一侧，而且差距的两端恰好是本仓最值钱的两个机制：**换词重搜**（检索策略）与
   **ask**（引用契约）。本场里没有一次换词重搜：查询词就是整句问题。
2. **提示词加固只治一半**：加一句"即使你会也必须先查库"，凭记忆作答 **2 → 0**；
   但 ask 使用率仍是 **0/10**——"别凭记忆答"和"选对工具"是两件事。
   这条对"给用户什么默认建议"直接有用（已写进 `usage-guide.md` §2c）。
3. **工具本身站得住，探针证明**：走 ask 的 10 题里，6 道可答题全部带引用、
   **12 个 chunk_id 全部能 `read` 回**、0 越界；4 道不可答题全部 `refused=true`。
   **q017 是最说明问题的一题**：agent 臂里它搜到 5 条（含相关块 23）却答"库里没有
   相关内容"，探针臂里同一个问题 ask 给出了带引用的答案（`refused=false`）——
   **同一份库、同一个模型，工具选对就答得出，选错就报"没有"**。

**失败模式清单**（逐题原文留在 `build/mcp-tool-eval*.json`）：① 凭记忆作答；
② 零引用作答（search 只给片段，模型自己写答案自然没有 `[n]`）；③ **假否定**
（搜到却答"没有"）；④ 单发检索、不换词不追问；⑤ `ask` 从未被触发。
**协议层零错误**：参数全部合 schema、无未知工具、无工具报错、无超时。

**边界**：① 10 题是抽样；② 驾驶员提示词是人写的，换措辞数字会动（两臂提示词原文
都写进了 JSON）；③ 只测 local 档——api 档（DeepSeek 一类）预期显著更好，未测；
④ ask 探针测的是"工具本身能不能兑现引用契约"，不等于"agent 用起来能兑现"。

## 10. 证据自评 + 一次补检索：Self-RAG 最小闭包 A/B（2026-09-30）

**要回答的问题**：检索是一条单行道——首轮融合窗口之外的金块，生成阶段永远见不到
（hard 档 recall@10=0.931 就是那 12 道题漏在窗口外的部分）。让模型对**首轮命中**
自评一次"够不够答"，判不足就用它给出的新查询再检索一次，能不能把漏掉的证据捞回来？
这是清单第 5 项（技术路线谈判稿 §4 的 Agentic 最小切片），实现为
`retrieval.sufficiency_retry`（**默认关**，实验覆盖层 `build/sufficiency-local.yaml`）。

**怎么测**：两场 local 全量 63 题，同一份语料 / 题库 / 模型（qwen3:8b，
temperature 0.1、think=false、num_ctx 16384），**只差这一个开关**：

```bash
MIKASA_DATA_DIR=build/eval-local/data python -m mikasa eval run --profile local --name suff-off
MIKASA_DATA_DIR=build/eval-local/data python -m mikasa eval run --profile local \
    --config build/sufficiency-local.yaml --name suff-on
python -m mikasa eval compare <off_id> <on_id> --profile local   # 逐题配对 + bootstrap 区间
```

**闭包的口径**（实现见 `pipeline/sufficiency.py`）：自评只喂前 8 块的 200 字 snippet，
协议是**一行二选一**（`足够` / `不足：<新查询>`；解析不出=按足够处理）；判不足 →
新查询（跨语言档先译）再检索一次 → 新块去重后**追加在命中尾部、最多 3 块**（编号
`[n]` 走注入顺序，主命中必须稳定占位，与 `hop_expand` 同款）；自评调用异常/空查询
一律退回基线；mock 档恒不触发（ADR-0014 ③）。

### 10.2 结论（怎么读）

1. **不显著**：citation gold +0.030，CI 跨 0。63 题的样本量下，"补检索比不补更好"
   这句话**说不出口**；能说的是"方向为正、且正面案例集中在多金块 hard 题"。
2. **成本是确定的**：墙钟 +8.4%、输入 token +8.5%——自评调用**每题都发生**（63/63），
   而收益只在少数题上兑现。这是这类"先审后检"闭环的固有结构：审核费是固定的，收益是长尾的。
3. **触发率偏高**：59% 判"不足"（含 16 道不可答题"本就应该判不足"）。剩 47 道可答题里
   21 道（45%）也被判不足——即它对"够不够"的判定偏保守。10 题探针对照过"整块喂入
   （前 6 块全文）"的变体：可答题触发 3/7 → 2/7、不可答题 3/3 不变——**截断不是主因**，
   换个喂法不会把触发率拉回"理想水位"。（要压触发率得改判定机制本身，见下条。）
4. **默认关维持**（`retrieval.sufficiency_retry`），与 `hop_expand` / `structured_output`
   同款纪律：**没有显著增益的能力不进基线**，否则所有历史数字都要重标定。
5. **有价值的副产物**：这张表同时是"证据面宽度 → 引用面宽度"的一次实测——补检索把
   多金块题的引用数抬高（q021 3→6、q036/q037 +1），而拒答纪律纹丝不动（11/16、5 误答
   两臂相同）。将来若做"证据不足才拒答"的收口（把自评结果接进拒答路径，而不是接进
   检索路径），这里的触发率与判定分布就是现成的原料。

### 10.3 边界（诚实清单）

1. **单次跑 + 温度 0.1**：同一题两臂重跑能给出不同引用数（q045 实测），+0.030 的差值
   里有多少是抖动，这张表分不开。
2. **只测 local 档**。api 档（DeepSeek 一类）未测——那边自评的判定质量与成本结构都会不同。
3. **阶段 A 检索层差值为 0 是设计如此**：闭包挂在生成链路（`ask._retrieve` 与评测阶段 B），
   阶段 A 是"检索器本身"的固定口径，不经过闭包。别把它读成"闭包没改动检索"之外的意思。
4. **补检索只追加 3 块且不改排序**：这是保引用编号稳定的取舍（同 `hop_expand`），
   不是"补检索该有的样子"的唯一答案；若允许重排，收益上限会更高，代价是编号不再稳定。
5. **MCP `search` 刻意不接闭包**：它是纯检索工具，"会思考的搜索框"不是它（见 ask.py 注释）。

## 11. 论断级忠实性（claim 级 L2）+ RAGAS 对照（2026-09-30）

**要回答的两个问题**（评估清单第 6 项）：① 整段忠实性（裁判给一个 0/1）看不见什么？
把刻度拆到**断言**级能多看见什么？② 评测界的事实标准 RAGAS 四维与本仓手写口径
对表，能对上几维、对不上的地方差在哪？

### 11.1 claim 级 L2：整段判定的盲区（实测证据）

2026-09-30 在 20 题（抽样见 §11.3）上同时跑两把尺子：

| 口径 | 结果 |
| --- | --- |
| 整段忠实性（裁判 0/1，同批答案） | **20/20 全绿**（faithful=True） |
| claim 级核对（本仓自研，同一批答案） | 167 条断言：**161 支持 / 3 不被引用资料支持 / 3 无引用 / 0 未判定** |

**整段口径看不见的那 3 条断言**（落在 2 道题里：q033 两条、q036 一条）——这是
本次拆刻度的全部理由：一条越界断言藏在三条正确断言里时，整段判定照旧给"忠实"。

口径要点（细节见 ADR-0042）：

- **证据面 = 该断言自己引用的块**（`[n]` → 第 n 条注入片段），不是全部检索上下文。
  本仓 L2 的定义是"**引用**是否真的支持所声称的陈述"；用全库上下文验证会把
  "引用挂错块、但内容碰巧也在别的命中里"判成支持，丢的正是引用协议守的那条线。
- **无引用断言（`uncited`）**：行首没有 `[n]` 的事实陈述——既不能算被支持、也不能算
  被证伪，单独披露（"答案里多少事实陈述根本没挂引用"本身就是纪律信号）。
- **未判定（`undecided`）**：解析不出结论的断言。与裁判"没测到 ≠ 不忠实"同款纪律。
- **默认关**（`judge.claims`）：每题多两次裁判调用，只在需要细刻度的场次打开。

**踩坑留档**：首版解析器只认 `1: 是`，而 Qwen 把逐条判断写成有序列表（`1. 是`）→
20 题里 16 题的断言整批记成"未判定"（表面像模型没答，实际是解析器没读）。修法：
分隔符集合收进 `.、)）。`，并加回归测试。**指标为 0 时先怀疑读的人**——与
2026-09-27 的"畸形标记统计盲区"同源。

### 11.2 与 RAGAS 的映射表（"对外可比"的那一页纸）

| 本仓口径 | RAGAS 口径 | 关系 |
| --- | --- | --- |
| **claim 级支持率**（断言 → **其引用块**是否支持） | **faithfulness**（断言 → **全部检索上下文**是否支持） | 同一刻度（断言级）、**证据面不同**：本仓只认引用闭包，更严；两者的差就是"引用挂错块"这类问题 |
| 整段忠实性（裁判 0/1） | —（RAGAS 无整段粒度） | 本仓独有；claim 级正是它的补丁 |
| **citation gold ratio**（引用块命中题面 `gold_chunk_id` 的比例） | **context precision**（检索上下文相对参考答案的信噪比） | 块级对 gold ↔ 句/段级对 reference；同向、**不同刻度**，数字不可直接比 |
| recall@k（gold 块在不在前 k 名） | **context recall**（参考答案的每个要点能否在上下文里找到） | 同上：块在不在 ↔ 要点在不在 |
| 裁判 correctness 1-5 | answer relevancy（答案与问题的嵌入相似度） | **不同轴**：本仓量"对不对"，RAGAS 量"贴不贴题"——四维里唯一没有对应物的一维 |
| 拒答纪律（可答误拒 / 不可答误答 / L3 违规） | —（RAGAS 不测拒答） | 本仓协议层独有；这也是 LangChain 对照里框架侧 0/16 拒答的同一件事 |

### 11.3 RAGAS 对照（2026-09-30，同 20 题、同答案、同上下文）

**协议**：api 档（DeepSeek 生成）、语料 `build/eval-api/data`（57 块）、从 47 道可答题里
**分层抽样 20 题**（种子 `20260930` 写死）；答案与上下文由产品链路一次导出
（`experiments/ragas_baseline/export_answers.py`，与评测阶段 B 逐字同轨），RAGAS 侧只读、
不重跑——两边吃的是同一份东西。裁判用**与主仓同一个** Qwen2.5-72B（SiliconFlow），
嵌入同家 bge-m3。对照目录见 `experiments/ragas_baseline/`，逐题表在 `out/result.md`。

| 口径 | 本仓 | RAGAS（同 20 题） |
| --- | --- | --- |
| 断言级忠实性 | claim 支持率 **0.982**（161/164 条断言；无引用 3、未判定 0） | faithfulness **0.973** |
| 整段忠实性 | 裁判 **1.000**（20/20 全绿） | — |
| 引用/上下文质量 | citation gold ratio **0.724**、越界 **0** | context precision **0.987** |
| 召回 | 见评测报告阶段 A（本题集的 gold 块是否进窗） | context recall **0.925** |
| 答案与问题 | 裁判 correctness **4.80**/5 | answer relevancy **0.422** |

**三条结论**：

1. **忠实性两把尺子对得上，且差异可解释**。0.982 vs 0.973 是同一刻度上的两个数：
   本仓证据面只认**该断言自己的引用块**（更严），RAGAS 用**全部检索上下文**。
   逐题看：q033 两边都指出问题（我方 2 条未支持 / RAGAS 0.875）；q036 我方指出 1 条、
   RAGAS 判 1.000——**正是"引用挂错块但内容在别的命中里"这一类**，只有引用闭包口径看得见；
   q046 反过来（RAGAS 0.667、我方 0 条未支持），是断句与断言切分粒度不同所致。
   **两把尺子都不是错的，量的是不同的"依据面"。**
2. **answer relevancy 在中文语料上被语言系统性压低，不可跨语言比大小**。0.422 看着吓人，
   但复现探针把原因钉死了：RAGAS 的这条提示词与示例**全是英文**，Qwen 于是把中文答案的
   "反向问题"写成英文——实测 q004：原问题（中文）↔ 反向问题（英文）的 bge-m3 余弦只有
   **0.584**，量的是**跨语言相似度**，而英文论文里的 0.8~0.9 是单语相似度。这不是"答案
   不贴题"：同一批答案上裁判 correctness 是 4.80/5、citation gold 0.724。**报这个数必须
   连语言一起报**，否则就是拿两把不同单位的尺子比长短。
3. **context precision 0.987 与 citation gold 0.724 的落差是粒度的落差**。RAGAS 量的是
   "整个检索窗口相对参考答案的信噪比"（14 块里大部分确实相关），本仓量的是"**被引用的**
   块有没有命中题面 gold"。一个宽、一个窄，两个数都真，混在一张表里比大小没有意义——
   这正是谈判稿里"粒度不可比"那条预判的实测版。

**边界**：① 20 题抽样、单次跑；② 只用 api 档（RAGAS 四维都要 LLM 裁判，local 档跑不起）；
③ 版本钉死在 `requirements.txt`（ragas 0.3.1 + langchain 0.3.x，0.4.3 与
langchain-community 0.4.x 是坏组合）；④ 依赖 99 包 / 591 MB 的**对照组环境**，
不进 `src/`、不进主 CI，主仓只留本节。

**复跑**：

```bash
MIKASA_DATA_DIR=build/eval-api/data .venv/Scripts/python.exe \
    experiments/ragas_baseline/export_answers.py --out experiments/ragas_baseline/out
experiments/ragas_baseline/.venv/Scripts/python.exe \
    experiments/ragas_baseline/run_ragas.py --out experiments/ragas_baseline/out
.venv/Scripts/python.exe experiments/ragas_baseline/compare.py
```

**两个踩坑（细节见对照目录 README §5）**：① `pip install ragas langchain-openai` 这种
联合求解会在 langchain-core 的版本区间上回溯半小时以上——**先装 ragas 再补其余**；
② RAGAS 默认并发会把 SiliconFlow 打到 429，ragas 把失败静默记成 NaN（首轮 20 题里
7~14 题整条指标是 NaN，均值只在幸存样本上算）——**压并发 + 重试，并把失败数写进结果**。

## 12. 检索口径与候选深度：两套数、一次零成本 A/B（2026-09-30）

**为什么写这一节**：2026-09-30 拿用户的**真实语料**（《循环荷载作用下螺旋锚的工作
性能》，911 块 / 29.4 万字 / 189 页，正文以英文为主）现场出了一套 21 题的题库
（`build/user-corpus/golden-user.json`，走 ADR-0026 的自动出题），跑出来的成绩与
样例语料差了一大截——而差的那截**大半是口径**，不是能力。

### 12.1 阶段 A 是"单路"，产品是"两路"：同一批题的 0.500 与 0.94

| 口径 | 做法 | 该语料 top-10 命中 |
| --- | --- | --- |
| 阶段 A（报告里的 recall@10） | **只喂原问题**、关重排、窗口锚定 10 | **8/16 = 0.500** |
| 产品问答链路 | 原问题 + **中文问题→英译的第二路**，双路 RRF 合流（`retrieval.crosslingual`） | **15/16 = 0.94** |

**机制**：提问是中文、正文是英文。单路时金块在 BM25/向量两路分别落到 39~546 名与
43~764 名（中文嵌入模型对英文正文的语义匹配很弱，BM25 只能靠数字/符号偶然命中）；
**译成英文再检索一次，7 道题立刻回到 top-10**，只剩 1 道（a013）救不回来。

**结论（写进报告口径）**：阶段 A 刻意不调 LLM（可复现），因此它**系统性低估**了
跨语言场景下的产品召回——阶段 B（产品真实链路）才是那类语料的成绩。评测报告现在
在阶段 A 表头上直接写明这一点。

### 12.2 候选深度 20 → 60：样例语料零回归、真实语料 +2 题

**动机**：融合只看得见**两路各自的 top-20**（`bm25_top_k` / `dense_top_k`）——金块
若排在 20 名之外，窗口再宽、加不加重排都救不回来。真实语料上 16 题里有 7 题的金块
就在 20 名之外（其中 2 题紧贴边界：24 / 30 名）。

**做法**：镜像阶段 A 的取数（关重排、窗口锚定 `RETRIEVAL_FUSION_TOP_K`），**只把
两路深度从 20 改成 60**，两组题库各跑一遍，逐题配对 bootstrap（零 LLM 调用，几十秒）。

| 题库 | recall@5 | recall@10 | MRR | nDCG@10 | 逐题 |
| --- | --- | --- | --- | --- | --- |
| 样例语料（47 题，回归） | 0.982 → 0.982 | 0.982 → 0.982 | 0.924 → 0.924 | 0.933 → 0.933 | 救回 0 / 挤出 0 |
| 真实语料（16 题） | 0.500 → 0.562 | **0.500 → 0.625** | 0.406 → 0.432 | 0.431 → 0.480 | 救回 **a007 / a013** / 挤出 0 |

配对区间：真实语料 recall@10 **Δ+0.125，CI [0.000, +0.312]** → 按"区间不跨 0"的
判据**不算显著**（下界正落在 0，n=16 太小），但**方向一致、零回归、成本是一行配置**。
样例语料 delta 恰好 0（47 题的候选池本来就够宽），说明这一步**不会伤到已达标的那档**。

**未做**：把这行改动落进 profile（它会动基线，按纪律要记账 + 全档回归）；也没测
更大的深度——扫描显示 ≥100 之后池覆盖不再增长（14/16 封顶），剩下的 2 题是**语义
鸿沟**（中文问题、英文正文、无数字可蹭），得靠查询改写或换嵌入，不是深度能解决的。

**边界**：真实题库是**自动生成**的（部分题面是陈述句、单金块），所以那里的绝对数字
只能看方向、不能横向比；`citation gold` 在"一题只认一块金块、而正文有 911 块"的
语料上天然偏低。
